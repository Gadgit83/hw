# Network play: what exists and what could be reused

This is a survey, written while building the 0.2.0 setup screen, of what Hedgewars already has for network play, so that a party mode or a network mode is designed on what exists. Nothing here is built into the app. Paths are relative to the repository root (https://github.com/Gadgit83/hw, branch `android-master`, which is upstream master plus the Android commits and this app) unless they start with `project_files/Android-native/`, and each was checked to exist when this was written. Where something is a reading of the code and was not run, it says so.

## Where the app stands

Update, build 0.3.0-mp1: this survey describes 0.2.0. The app now has an experimental relay that lets phones play each other (README, Network games); the relay is a small Java one written for this app, not the Haskell or Rust server surveyed below. The rest of this page is unchanged.

- The app is hotseat only. One phone runs the engine, all teams play on that phone, and computer teams are played by the engine's AI.
- The engine runs as a client of a local IPC socket on 127.0.0.1. The launcher (`project_files/Android-native/native/launcher/hp_ipc.c`) stands in for the Qt frontend on that socket and serves the game setup from `files/game.ipc`.
- SDL2_net is linked only because the engine uses it for that local IPC socket (`project_files/Android-native/native/CMakeLists.txt`). The app does not open any other connection. (The manifest requests `INTERNET`, which Android requires for any socket, loopback included.)
- There is no LAN play and no way to find or join another device. Without a relay server of some kind, none of the below works: Hedgewars network games are always client, server, client; two engines never talk to each other directly.

## Teams in a network game (0.3.0-tv17): protocol

The host configures the game's teams on its Setup screen (its own teams and the computer teams), and its hello carries all of them, as before. A joining phone sends only its own team: "Your team" on the Network screen, a saved team chosen there (default: the first human team of its setup, else the first team), editable with the team editor. Its hello `teams` list therefore has one entry. The hello format is unchanged (no proto or compat bump).

- Relay: no per-phone minimum or cap. A player with one team is accepted. The game needs at least two teams in all (`canStart`, and the start notice says so); a team clash is still settled at Start (colours), as before.
- New lobby message, host only and only before the game: `{"t":"remove","id":N}` takes a joiner out of the lobby, with its team. The joiner gets `{"t":"closed","reason":"The host removed you from the game. ..."}` and its lobby link is closed. Sent by a joiner, or during a game, it is ignored.
- A joiner whose lobby link is up can send its team again with `{"t":"teams",...}` (the "My team again" button): one team, as above.

## Game password (0.3.0-tv12): protocol

Update, 0.3.0-tv12: a network game can ask for a 4-digit game password (PIN). This is the protocol of the phone relay (`app/src/main/java/org/hedgewars/android/net/Relay.java`) as the phones and the TV viewer use it. `Compat.VALUE` is now `hwnet-60-sim2` (`protocol` stays 60), because phone and TV must agree on the new fields.

- Host: setting "Game password", off by default (0.3.0-tv13; the choice is kept). While on, each hosting session gets a random PIN, 0000 to 9999 (always 4 digits, leading zeros kept, `java.security.SecureRandom`), shown large in the host lobby with Change (type exactly 4 digits, or make a new random one). Off: anyone on the Wi-Fi may join or watch. A change applies to new connections only; phones already in stay in. The relay holds the PIN (`Relay.setPin`, `Relay.getPin`, thread-safe).
- Status GET on the viewer port (8766): new boolean `pin`, true when a password is set. A GET never needs the PIN and is never counted as an attempt.
- NSD TXT record: `pin=1` when a password is set, `pin=0` otherwise (a host that does not publish the key is read as no password). The phone's Join list shows "Asks for a game password" and asks for the PIN before connecting. The record is registered again when the host switches the password on or off.
- TV viewer WebSocket (0.3.0-tv13): the game password never applies to TVs. The request may still carry `pin=NNNN` and `compat=`; `pin` is ignored. With no game running the answer is 503, otherwise the stream starts. The relay never sends a TV close code 4006 or 4007 (0.3.0-tv12 did), and TV attempts are not counted towards the lockout.
- Phones (TCP 46633): the lobby hello has a string field `pin`. It applies to Join to play and to Join to watch. Missing or wrong: the refuse message `{"t":"refuse","code":"password","reason":"Wrong password."}`. Locked: `{"t":"refuse","code":"password-locked","reason":"Too many wrong passwords. Try again in 30 s."}`. The host's own loopback connection (it presents the host secret) needs no PIN. A refusal for the version, data or host role has no `code`.
- Brute force: per source IP address, phones only (TVs are not counted), per hosting session. The 5th wrong or missing PIN is answered as wrong and locks the address for 30 s. During the lock every attempt, the right PIN too, gets the locked answer and does not extend the lock. A right PIN clears the address's count. Entries not seen for 5 minutes are forgotten and the table holds at most 512 addresses.
- Joining phone: a host that advertises `pin=1`, or a join refused with `code` `password`, brings up a 4-digit entry with a numeric keyboard; a typed-address join refused for the password asks and joins again. The last accepted PIN per host is kept in memory for the app session, so a re-join does not ask again.
- Logs: the PIN is never written to the relay log, the Android log or the report; they say "game password set" or "off".
- Checked in `RelayTests.testGamePassword` and `testHostAdvert` (`scripts/net-test.sh malformed`); the net-test scenarios run with a PIN (`NetHarness.PIN`), the phones and the TV stand-in send it.

## Rejoining a running game (0.3.0-tv14): design

Update, 0.3.0-tv14: a phone that loses its connection in a running network game, or leaves it with Back, can come back within two minutes, and the host can leave the game without ending it. The relay and the launcher do this with messages the engine already has, plus one engine rule added for issue 22 (see Teams back). Everything below was run with the real engine (`scripts/net-test.sh rejoin`, `rejoinlate`, `hostleave`, `hostend`) and with the fake engines of `RelayTests`.

**The seat.** A phone keeps its seat (its `Player` in the relay) for the whole game. When its connection is lost (engine link closed, the liveness ping or the silence rule, a full queue, a lobby link that is gone for good) or it leaves (control frame `\0Q`: Back > "Leave the game", or the engine's own quit; the host's too), the relay injects the unsynced team-gone `F<team>` for each of its teams, as it always did, and now marks the seat away for `Relay.Config.rejoinMs` (120000, two minutes). The others and the TV just see the teams sit out (the engine skips their turns). Notices: lobby `notice` messages and a chat line written into the game (message `s`, through the log, so every engine and a late joiner or TV shows it): "<name> lost connection; waiting up to 2 minutes for them to rejoin" (or "<name> left the game; ..."), "<name> is back", "<name> did not come back; their teams sit out". A desync, a map digest that differs after a rejoin and a phone that never linked in the first place are dropped for good.

**Who is who.** At join the relay sends `{"t":"joined","you","name","rejoin":"<token>"}`; the token is 128 random bits and never appears anywhere else. A joining phone writes host, port, its (unique) name and the token into `files/rejoin.txt`, so it survives the app being killed; it is deleted when the game is over or the phone leaves a lobby with no game running. Coming back needs the token and the same name: `{"t":"hello","role":"lobby","rejoin":"<token>","name":...}` on a new lobby link (the game password is not asked again; the token is the proof), or `{"t":"rejoin"}` over a lobby link that is still up. A wrong token, another name, a seat of the host and a seat that does not exist get the same refusal (`rejoin-unknown`, "This seat is not yours, or the game it belonged to is over."), so nothing is learned about other seats. The host's seat comes back the same way: `rejoin` over its own lobby link while that link is up, or a new loopback link with the hello (`host` true, the host secret, its token and name). The app keeps the host's note in `files/rejoin.txt` as well (`seat=host`), and offers it only while the hosting service runs. A phone that comes back before the relay noticed it was gone (half-open links) takes the seat over: the old links are cut.

**Catch-up.** The relay answers with a `start` message with `"rejoin":true`: the canonical setup lines with every team `erdriven` (driven from outside, as for a watcher), `eowner <name>` after the `erdriven` line of the phone's own teams, `TN`, and `e$spectate 1` at the end, and a new engine token (the old one is dead). The phone starts a new game process exactly as at the start of a game. When its engine link is up the relay sends the whole game log so far in one go, then the live stream (the same snapshot-and-register step under one lock that a watcher gets, so nothing is lost or doubled). The engine fast-forwards through the log. Its own teams replay correctly because their moves are in the log, which is why they are `erdriven` during the replay. Until the teams are back, whatever that engine sends is not forwarded (a map digest is compared with the game's: a different map drops the phone for good).

**Teams back.** In `hedgewars/uTeams.pas`, `chTeamBack` runs in two steps. The unsynced message `G<team>` (engine message `G`, read by `uIO.pas` like `F`, no timestamp) only sets a pending flag on the team, and the engine whose *current team is one of its own* (not driven from outside) turns it into the synced `g<team>` at once and sends it. The synced `g` is read by all engines in the log: the team's `hasGone` is cleared and, only if the pending flag is set *and the team's `Owner` equals the engine's `UserNick`*, `ExtDriven` goes false, so the team becomes local on that phone only. That is why the rejoining phone's setup has `eowner <name>` for its own teams (and only there: on the other phones the owner stays empty, so they never take the team), and why the launcher passes `--nick` in base64 (the engine, started with `--internal`, decodes it; it used to be garbled). The relay asks for the team back with `G<team>` in the log, normally only **right after a message from a live phone from inside its own turn** (not a turn end or a map digest): while every team in play is a gone team no engine can answer, and the unsynced message alone would be lost. When no other phone is playing (the game is held, every phone away), the phone coming back is asked itself, at once. It asks again after `backResendMs` (2.5 s) if no `g` has been seen, and stops after `backWaitMs` (90 s). When the relay sees the synced `g` for each of the phone's teams it forwards what that engine sends again. A phone that is still catching up has its own team's `g` taken (`ownTeamBack`) and nothing else of it.

One engine rule serves the lone case (issue 22, `uTeams.pas`, `chTeamBack`). A phone that rejoins alone has every team driven from outside, so no team of its own is in play to answer for it. The relay therefore starts such an engine with `eloneback 1` (only when no other phone is playing when it comes back), and that engine, and only that one, answers the ask for its own teams (`Owner = UserNick`) and sends the synced `g`, even though its current team is driven from outside. An engine started without the flag never answers for its own teams: another engine answers, as before. Without the flag a second answer would reach the log from a phone that is out of step with the others. A phone that came back while another phone was still playing gets the same flag live, when the others have all gone away while its teams are still pending: the relay sends the control frame `\0L`, and the launcher passes it on to the engine as the local command `eloneback 1` (`hp_ipc.c`, like the pause). Only the engine that was told it is alone answers for its own teams.

**After the window.** The seat is given up: `{"t":"gaveup"}` to the phone if it still has a lobby link, the teams stay gone, and a rejoin is refused with `rejoin-late` and the text "You were away too long; the game went on without your teams. You can watch." (The Network screen then offers Join to watch.) The seat is dropped from the lobby at the end of the game if its lobby link is gone.

**Ending.** The game does not wait for an away phone if the phones that are still in it have all seen the game over ("every engine finished"). If every phone is away the game is **held**: nothing is sent, nobody is dropped by the silence rule (a seat that is away is not blamed), and the first phone that comes back is let in alone; its teams come back as above (the relay notes "every player is away: the game is held" once). Otherwise the game waits inside the windows and ends when the last window has run out: reason "Every player left the game and nobody came back" (`Relay.NOBODY_LEFT`, TV close code 4005); when a window has run out and nobody is connected, at once. The host leaving the game (Back > Leave the game, the engine's own quit) is a leave like any other: the relay, the TVs and the other phones carry on; its seat is away for two minutes and it can rejoin, also when nobody else is playing (the game is then held for it). The host's "End the game for everyone" sends the control frame `\0Z` first (accepted from the host's link only; from anyone else it is logged and ignored), then its engine quits: the relay ends the game for everyone as before ("The host ended the game", TV close code 4001). The hosting service stopping or dying, and the host's Wi-Fi going, end the game as before (4004, 4003). While a phone is away the game just goes on; there is no pause.

**What the engine does that cannot be changed here.** A team that is gone has its turns skipped, and after three skipped turns the engine kills the team's hedgehogs (`TeamGoneEffect` in `uTeams.pas`). In a long game with few teams a phone that was away for most of the window may come back to a team that has no hedgehogs left. The rejoin itself still works (the team is back, with nobody left to play).

**TV overlay (viewer protocol, 0.3.0-tv14).** The TV WebSocket on 8766 carries the game as binary frames (opcode 2) as before. Between them the relay sends WebSocket text frames (opcode 1, UTF-8 JSON) through the same per-viewer queue, so they arrive in stream order: `{"t":"away","name":"<player>","leftMs":<ms left in the rejoin window, 120000 at the start>,"onPurpose":<true if the player left through the Leave control frame, false if the connection was lost>}` when a seat goes away; `{"t":"back","name":"<player>"}` when the player has rejoined and its teams are back (the synced `g` seen); `{"t":"gaveup","name":"<player>"}` when the window runs out. A TV that connects (or reconnects) while a seat is away gets, after its first (backlog) binary message, one `away` frame per away seat with the `leftMs` remaining at that moment. Names are JSON-escaped. Text frames go to TV sockets only: never to the phones' engine links, never into the game log or the backlog. A TV client must ignore text frames it does not know (the e2e stand-in `viewer-sim.js` keeps them apart in `overlay`).

**Wire summary (new in 0.3.0-tv14).** Lobby, relay to phone: `joined`, `gaveup`, `rejoin-refused {code, reason}`, `start` with `rejoin`; player entries in `state` have `away`, `gaveUp`, `awayLeftMs`. Phone to relay: hello field `rejoin`, `{"t":"rejoin"}`. Engine link, phone to relay: control frame `\0Z` (host: end for everyone). Engine link, relay to phone: `G<team>` and `s<chat text>+2 bytes` in the stream, so a TV that shows the stream sees them too.

Checked in `RelayTests.testRejoin`, `testLoneRejoin` and `testRejoinWindow` (`scripts/net-test.sh malformed`) and in the net-test scenarios `rejoin`, `rejoinlate`, `hostleave`, `hostend`, `hostquit`, `lonerejoin` (the host comes back alone) and `lonerejoinb` (the joiner comes back alone).

## Control frames (engine link, phone to relay)

A frame whose first byte is 0 is a control frame on the engine link. The launcher sends them; the relay reads them only from the sending phone's own engine link. Anything else the launcher does not know is ignored.

| Frame | From | Meaning |
|-------|------|---------|
| `\0K` | the relay pings, the launcher answers | liveness: the link is up (half-open check) |
| `\0E<text>` | any phone | engine error |
| `\0Q` | any phone | the player confirmed leaving (seat kept for the rejoin window) |
| `\0Z` | host only | "End the game for everyone" |
| `\0P` / `\0R` | host only | pause / resume (the relay answers to every engine) |
| `\0H` | any joined phone, a watching phone too | the app went to the background (the game activity stopped): see below |
| `\0V` | the same | the app is in front again |
| `\0X<text>` | relay to phone | the relay ends the game (the reason follows) |

A watching phone's launcher sends its own `\0Q`, `\0H` and `\0V` and its game over; the relay ignores its other control frames. A watching phone's `\0H` and `\0V` only affect its own liveness check (see below).

## Hidden phones (0.3.0-tv17, issue 17): design

**The problem.** A joining phone's lobby link lives in the app process. Android 14 and later freezes a cached background app within seconds, so a phone whose app was merely hidden (home screen, another app, screen off) stopped answering the lobby pings and the engine's pings. The relay then dropped it ("lost connection; waiting up to 2 minutes"). Only a real close should count as leaving.

**What the app does.**
- A joined phone (player or watcher) runs `JoinService`, a foreground service of type connectedDevice (a notification "In a network game on <host>"), from the join until it leaves the session (`NetSession.leave`, or the lobby link closing). The process is not frozen while the service runs, so the lobby link keeps answering. The wake lock and Wi-Fi lock are taken by `NetSession` for the same time. A finished game does not stop the service: the phone goes back to the lobby and its link must stay alive there.
- When the game activity (`GameActivity`, the `:game` process) stops in a network game, the launcher sends `\0H` to the relay; when it starts again, `\0V`. The launcher queues these behind the game messages (it never waits, the call is on the UI thread). A local game sends nothing.
- SDL pauses the engine thread when the activity stops, so the engine sends nothing while hidden. The launcher's send and receive threads (`hp_ipc.c`) are separate pthreads and keep answering the relay's `\0K` pings.

**What the relay does** (`Relay.java`, `Config.hiddenMaxMs`, 600000 ms = ten minutes in the app).
- While a player is hidden (`\0H` taken, no `\0V` yet, and the limit has not run out) the silence rule does not blame it, the link-ping check does not drop it, and the map-digest wait does not drop it. Its turns still wait or are skipped by the normal rules: nothing else changes.
- A real close of its engine link still drops it at once, into the rejoin window as before.
- Hidden for longer than `hiddenMaxMs`: the phone is dropped as a lost connection (its rejoin window applies: "its app was in the background for more than 10 min").
- `\0V` ends the exemption at once; a phone whose link drops, or who starts a new game, is not hidden any more.
- In the lobby nothing changes: the relay's lobby keepalive (ping every 5 s, removal after 25 s of silence) is answered by the app process, which the service keeps running.

**Known limits.** The freeze of the `:game` process is not stopped by `JoinService` (it runs in the main process). The relay's tolerance is what covers a frozen game process, while its TCP link stays open (the kernel keeps accepting data for it). Whether Android keeps that socket open for ten minutes on a real phone is not verified here: it needs the owner's test. Samsung's background limits may also stop the service; the notification says what is running.

**Tests.** `RelayTests.testHidden` (`scripts/net-test.sh malformed`): the silence rule is held off while hidden and applies again after `\0V`; a real close while hidden drops at once, into the rejoin window; hidden longer than the limit drops; the link-ping check is held off while hidden. The net-test scenario `hidden`: phone B hides after a few turns, its engine sends nothing for 40 s (longer than the 20 s silence rule), then it is in front again; B must not be dropped, 0 desync, a normal game over.

## How a Hedgewars network game works

The engine is deterministic lockstep. Every client simulates the whole game from the same setup and the same ordered inputs; nothing about the game state is sent. That is what makes it cheap to carry over a network, and also what makes a mismatch fatal.

**Engine side** (`hedgewars/uIO.pas`, `hedgewars/uCommandHandlers.pas`):

- The frontend starts a network game by sending the engine `TN` instead of `TL` (`ParseIPCCommand` sets `GameType := gmtNet`). The rest of the setup lines (`etheme`, `eseed`, `e$...`, `eaddteam`, `eaddhh`, and so on) are the same as for a local game. In a network game the Qt frontend marks other players' teams with `erdriven` (`QTfrontend/team.cpp`, `teamGameConfig`), which sets `ExtDriven`, so the engine takes that team's moves from the network.
- Every command of the team that is being driven locally is sent out through `SendIPC` (letters such as `L`, `l`, `R`, `r`, `A`, `a`, `j`, `J`, `S`, `,`, slot numbers 128 and up, and `N` for the end of a turn; `isSyncedCommand` lists them). Each carries the low 16 bits of the game tick, and `#` raises the high half. The frontend collects these (`HWGame::ParseMessage` default case, `flushNetBuffer`, `m_netSendBuffer` in `QTfrontend/game.cpp`) and sends them to the server.
- Messages from the other players come back to the engine through the same IPC socket and are queued by tick (`NetGetNextCmd` in `uIO.pas`); the engine runs the game only as far as the ticks it has been given, so a slow player makes everyone wait at their turn.
- Desync detection is in the engines, not the server. At the end of a turn the local engine computes a checksum over the game tick and every gear (`chNextTurn` in `uCommandHandlers.pas`, which calls `gear_checksum` from the Rust library) and sends it inside the `N` message. Every other engine computes the same checksum at the same point and compares it with the one that arrived (`lastTurnChecksum`, set when `N` is read in `NetGetNextCmd`); a difference stops the game with `Desync detected`. Because the checksum depends on the floating point style maths, collision and map generation, all clients must run identical engine code. On this port that code is the Rust library `libhwengine_future` plus the pas2c output, the same as upstream's, which is why the simulation was kept identical to upstream (decision D2 in the party project's log, https://github.com/Gadgit83/hedgewars-party, `docs/decisions.md`). Not tested here: a network game between this build and a desktop build.
- The network protocol number the engine expects is `cNetProtoVersion`, set at build time (`HEDGEWARS_PROTO_VER` is 60 in `CMakeLists.txt`; `hwengine --protocol` prints it).

**Official server, Haskell** (`gameServer/`, built from `gameServer/hedgewars-server.cabal`, entry point `hedgewars-server.hs`; default port 46631 in `gameServer/CoreTypes.hs` and `gameServer/Opts.hs`):

- The protocol is lines of text; a message is a few strings separated by newlines and ended by an empty line (`CONNECTED\nHedgewars server ...\n3\n\n`). It covers nicknames, protocol check, lobby, rooms, teams, scheme and map settings, chat and the game itself. The handlers are `HWProtoCore.hs`, `HWProtoLobbyState.hs`, `HWProtoInRoomState.hs`, `HWProtoNEState.hs` (clients that have not entered the lobby yet), with the actions they trigger in `Actions.hs`.
- Engine traffic travels as `EM` messages: base64 of length-prefixed engine IPC messages (`toEngineMsg` in `gameServer/EngineInteraction.hs`; the Qt client builds the same in `QTfrontend/net/newnetclient.cpp`, `RawSendNet("EM...")`, and decodes incoming ones into `FromNet`).
- The server is a relay, not a simulation. For an `EM` from a client, `handleCmd_inRoom ["EM", msg]` in `HWProtoInRoomState.hs` passes it through `checkNetCmd` in `EngineInteraction.hs`, which keeps only message types from a whitelist (`legalMessages`, the same letters as above plus chat and a few others), rejects a malformed hedgehog-say message, and works out which of the messages are timed. The legal messages are forwarded to all other clients in the room (`AnswerClients chans ["EM", legalMsgs]`), and the non-empty ones are stored in the room (`roundMsgs`, `lastFilteredTimedMsg`) so that a player who joins late, or a spectator, can be sent the whole game so far (`HWProtoLobbyState.hs`, `HWProtoInRoomState.hs`).
- The server does not compute or verify the checksum; it relays `N` like any other timed message. Detecting a desync is left to the engines, as above.
- Room admin, scheme and weapon set changes, votes (`Votes.hs`), flood detection (`FloodDetection.hs`) and the replay checker (`HWProtoChecker.hs`, official server only) are also here.

**Rust port of the server** (`rust/hedgewars-server`, with the protocol in `rust/hedgewars-network-protocol`):

- A tokio based reimplementation of the same server and protocol: `src/main.rs` (listens on 0.0.0.0, port 46631 by default, `-p` to change), `src/server/network.rs` (connections), `src/core/` (clients, rooms, server state), `src/handlers/` (in the lobby, in a room, and so on; `inroom.rs` has the `EngineMessage` handler that does the same validate and forward as the Haskell one). It builds without the official-server features (MySQL, TLS are optional cargo features).
- `rust/hedgewars-network-protocol` holds the message types (`messages.rs`), a nom parser (`parser.rs`) with the framing documented at its top, and tests. Its types are a usable description of the whole protocol and could be used from a Rust or JNI hub. Whether the Rust server is complete enough to replace the Haskell one was not tested here.
- It is the nearest thing to a server that could be embedded in an Android app: a single static binary or library with no GHC runtime, Linux and Android capable in principle (cargo targets are already used for `libhwengine_future.so`). Not built or tried here.

**Qt desktop client** (`QTfrontend/net/newnetclient.cpp`, `.h`, `tcpBase.cpp`; `QTfrontend/game.cpp` for the engine side): connects to the server, checks the protocol (`CONNECTED` and a minimum server version), handles lobby and room messages, and relays `EM` messages between the server and the local engine. A good reference for the order of messages in a real session.

**Old C client library** (`project_files/frontlib/`): a C reimplementation of the frontend's networking and engine IPC for the old Hedgeroid Android port (it has an `Android.mk`; `net/netconn.c`, `ipc/gameconn.c`, `model/`), using SDL_net 1.2 (`CMakeLists.txt` asks for SDL, SDL_net and zlib). It was written against an older protocol version and was not built or tested here; it is not part of this build. Read it as a second description of the client side, not as code to reuse unchanged.

**WebWars gateway** (`upstream/webwars/gateway/src/index.js`, from the WebWars clone that sits next to the engine checkout and is not tracked here): a Node.js process that accepts WebSocket connections and forwards each to a TCP connection to the Haskell server, turning each protocol message into a JSON array of its lines and back (`msg.join('\n') + '\n\n'` one way, splitting on `\n\n` the other). It is a small, working example of the pattern needed to put a browser or any WebSocket client on the existing server without changing the protocol.

## What this means for a party or network mode

No relay server exists in this app, so the first decision is where the relay lives. The options below are ordered by how little they ask of the engine.

1. **Local party, no Hedgewars protocol.** The host phone runs the engine for everything (as now). Controller phones are only input devices: they send button events to the host over a WebSocket on the LAN, the host feeds them to the engine as local touch or key events for the active team, and the TV gets a picture (decision D1 in the same log). No lockstep, no desync problem, no server. This is the plan in the roadmap and needs none of the code above, except possibly the lists of which commands the engine accepts (`doc/protocol.txt` documents the IPC commands, partly in Russian).
2. **Host phone as a Hedgewars server.** Embed the Rust server (`rust/hedgewars-server`, cross compiled for Android) in the app and let desktop or other Android Hedgewars clients join over the LAN with the normal Qt client. The host phone would also run an engine as a client of its own server (as a spectator or a player). The Android app would need a frontend for the lobby messages (`rust/hedgewars-network-protocol` gives the types and parser) and a way to hand the engine its `TN` setup and the `EM` stream, which is what `QTfrontend/net/newnetclient.cpp` and `QTfrontend/game.cpp` do on the desktop. Biggest work item: the client side (lobby, room, team and scheme handling), since the launcher today only serves a fixed setup file.
3. **Join an existing server** (official or self hosted). Same client work as in option 2 without hosting. The app already holds the `INTERNET` permission, and the engine on the phone must match the server's protocol number (`cNetProtoVersion`, 60 in this checkout) and produce checksums identical to the other players' engines. Because this port tracks upstream master and uses the same Rust simulation, that should hold, but it has not been tested.
4. **Web controller pages.** Controller phones need nothing installed if the host serves a page and a WebSocket (the WebWars gateway pattern, in reverse: the host is the server). This works with option 1 and does not conflict with 2 or 3.

Constraints and risks to keep in mind:

- A network game needs every engine on the same version; mixing this port with a desktop build is a desync risk until it has been tried. The checksum check will stop the game cleanly rather than let it go wrong silently.
- A Hedgewars game stops for everyone while one engine waits for inputs, so phones that sleep or lose Wi-Fi stall a game. The engine has a spectator mode (`e$spectate`, `chFastUntilLag`) that fast-forwards a late joiner, which is how the server catches players up.
- TV output is separate from all of this: Hedgewars network protocol carries no video, so a TV still needs the picture from the host phone (D1 in the same log) whichever of the options above is chosen.
- Licensing: the server and protocol code are GPL, like the engine, so anything built from them is GPL too. Fine for this project, but worth knowing before mixing in anything else.
